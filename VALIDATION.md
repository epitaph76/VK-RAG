# Проверки и измерения · 1–2 ноября 2026

## Понятная причина экстрактивного режима · 2 ноября

Пользователь сообщил об автоматических выдержках на запросе «а про deepseek последние какие новости» после обычного LLM-ответа на предыдущий вопрос. Первый повтор с `use_llm=true` вернул обычный ответ за 13,22 с. Следующий реальный запуск воспроизвёл переход в выдержки: `requested=true`, `attempted=true`, `status=fallback`, `fallback_reason=invalid_citations`, 26,88 с. Это отказ проверки привязки ответа к источникам, а не изменение переключателя. Причина именно исторического случая не устанавливается по одному скопированному тексту; на повторе получена конкретная диагностика. [Результат](benchmarks/generation-mode-checks.json).

Добавлены `meta.generation.requested/attempted/status/fallback_reason` и видимая плашка причины автоматического перехода. Таймаут, HTTP-ошибка, некорректный JSON, ID источников, цитаты и пустой ответ различаются. Ручное отключение генерации и отсутствие настройки LLM отображаются отдельно; переключатель не меняется сервером. История предыдущей версии совместима: плашка использует сохранённый `meta.llm_error`, если новых полей ещё нет.

`python -m pytest -q`: **65 passed**. Управляемые отказы шести типов сохраняют `requested=true`, дают `attempted=true/status=fallback` и точный код; отдельно проверены ручное отключение, отсутствие подключения и успешная генерация. TypeScript/Vite production build проходит. Повторные платные LLM-вызовы автоматически не добавлены; поведение ответа и поиска не менялось.

В браузере тот же DeepSeek-запрос после обновления получил обычный LLM-ответ за 15,1 с с тремя процитированными фрагментами, без плашки ошибки. [Экран обычной генерации](docs/generation-mode-normal.png). Автоматический переход и успешный ответ наблюдались на отдельных реальных запросах; это не утверждение о гарантированной доступности LLM.

## Исправление чрезмерных отказов · 2 ноября

Политика `context-v1` из предыдущего раздела оказалась слишком строгой: отрицательные логиты ошибочно трактовались как универсальный запрет, а проверка в основном подтверждала отказы. В корпусе есть полезная статья об AI-ассистентах, которую такая политика скрывала. Этот подход заменён; положительные результаты необходимы вместе с отрицательными проверками.

Гибридный поиск по смыслу E5/FAISS и по словам BM25 сохранён. Для новостных вопросов убирается разговорная обёртка, остаётся тема; decision-модели ищутся как модели принятия решений. Заголовок участвует в rerank. Новостные кандидаты ограничены тремя фрагментами одного документа, чтобы одна длинная статья не вытесняла остальные.

При подключённой LLM десять лучших кандидатов проходят смысловой отбор и генерацию за один вызов. Абсолютный порог логита перед ним не применяется. Ответ — JSON со статусом, ID и текстом; проверяются ссылки, возвращаются только реально процитированные источники. Используются `response_format=json_object`, лимит 2600 completion-токенов и инструкция о кратком ответе. При ошибке доступна локальная выжимка `context-v2`: явная поддержка темы может сохранить фрагмент с отрицательной модельной оценкой. Предложения для выжимки выбираются по теме и словоформам, а не по служебным словам исходного вопроса.

`python -m pytest -q`: **58 passed**. Добавлены положительные проверки ML и decision-моделей, отрицательная оценка при явном подтверждении темы, смысловой перефразированный ответ, корректность ID и ссылок JSON, даты и отбор предложений для локального режима. Отказы без подходящих источников также сохранены.

Реальные проверки Docker/sub2api: оба пользовательских запроса получают LLM-ответы и источники. В ML-ответе отсутствуют статьи про социальное обучение животных, Нобелевскую премию и кортизол. Запрос о decision-моделях использует исследование склонности LLM к риску. Без LLM запрос ML возвращает относящуюся к теме выдержку об AI-ассистентах; запрос о визе в Японию отклонён. [Результаты](benchmarks/semantic-recovery-checks.json). Отдельно в браузере повторён исходный ML-запрос: получен ответ с четырьмя источниками, ссылки и карточки отображаются. [Экран результата](docs/semantic-recovery.png). Свежесть относится к датам загруженного корпуса.

Это регрессионные проверки, не независимая оценка точности. LLM может ошибиться в смысловом отборе или содержании ответа; структурная проверка цитат этого не доказывает. Ранее сохранённые результаты `context-v1` ниже описывают заменённую версию, её чрезмерные отказы не считаются успешным итоговым поведением.

## Отбор релевантного контекста · 2 ноября

Воспроизведён запрос пользователя «какие последние новости в ml»: Laya запускала rerank, но все двадцать кандидатов имели отрицательные логиты; первым шёл фрагмент об оптогенетике с оценкой около −2,05. Старый `/ask` всё равно передавал первые пять в генерацию. Ранжирование само по себе не задавало критерий достаточности доказательств.

Добавлен отдельный `context-v1` перед генерацией и экстрактивным ответом. После rerank применяется настраиваемый порог сырого логита (по умолчанию 0, activation явно Identity). Без rerank используются значимые термины, Snowball-словоформы и, при наличии, порог Dense cosine. ML, AI/ИИ и LLM раскрываются при поиске. Отбор не вызывает дополнительный reranker: режимы `never` и уверенный `keep` сохраняют смысл. До пяти допущенных фрагментов, без обязательного заполнения квоты; при нуле LLM не вызывается. После генерации возвращаются только реально процитированные источники с перенумерацией ссылок. В LLM передаются даты публикаций и инструкция не перечислять посторонние темы.

`python -m pytest -q`: **50 passed**. Новые проверки охватывают отрицательные оценки, отказ без LLM-вызова, отсутствие животных в ML-контексте при fallback, различие шкал RRF/logit/cosine, отсутствие Dense, нормализацию словоформ, сокращения и перенумерацию цитат. API-регрессия показывает, что найденная по слову «обучение» статья о животных остаётся диагностическим кандидатом `/search`, но не попадает в `/ask`.

Реальные Docker-проверки на индексе `100-f749d38fb33b`: исходный запрос возвращает отказ и ноль источников в `auto`, `always`, `never`; вопрос о визе также отклонён. Вопрос «Почему древнейшего осьминога признали наутилусом?» получает пять допущенных фрагментов нужной статьи в экстрактивном режиме. [Результаты](benchmarks/relevance-checks.json). Положительная LLM-генерация в этой серии не запускалась; проверки её цитат выполнены тестами. Браузерная проверка остановлена механизмом Computer Use из-за невозможности уверенно определить URL окна Chrome; изменения проверены через API.

Пороги являются консервативными эвристиками, не калиброванной вероятностью релевантности. Возможен ошибочный отказ для подходящего материала. Пять контрольных запросов не заменяют независимую оценку на релевантных и нерелевантных примерах. Старые результаты 60 вопросов ниже относятся к прежнему корпусу и версии поиска; качество новой политики на них не заявляется.

## Устойчивость повторного сбора

Проверка новой частичной задачи показала отказ первого запроса к RSS Хабра, ещё до загрузки статей. Параллельного сбора в worker нет: источники и страницы обрабатываются последовательно. Во время диагностики тот же RSS трижды вернул HTTP 200 из контейнера с обычным TLS. Это подтверждает плавающий сетевой сбой, но не определяет, где именно он возник в сетевом пути.

Добавлены одна HTTP-сессия на источник, до трёх попыток временных GET-ошибок с ограниченным ожиданием и диагностикой RSS/HTTP/таймаута. Переадресации и повторы проходят проверку публичного URL; проверка сертификатов сохраняется. Повторы 403/TLS не выполняются. Успешное восстановление после двух таймаутов, предел повторов, Retry-After, разрыв потока и запрет локального редиректа проверены управляемыми тестами.

`python -m pytest -q`: **38 passed**; TypeScript/Vite production build проходит. Дополнительно проверены переиспользование неизменного индекса, принудительное перестроение и восстановление повреждённого индекса. Статус сбора показывает источник и страницы; счётчик фрагментов индекса подписан отдельно.

Реальный запуск «Обновить все» через защищённый API завершился за **42,51 с**: Хабр 40/40, «Элементы» 10/10, ошибок и дублей нет, `changed=0`. Сохранены 50 активных документов и 644 фрагмента. Готовый проверенный индекс переиспользован, его версия не изменилась. В этом живом запуске повторы не понадобились; механизм восстановления проверен тестами, а не искусственно представлен как сетевой инцидент. [Результат проверки](benchmarks/ingestion-reliability-checks.json), [экран](docs/ingestion-reliability.png).

## Benchmark

20 dev-вопросов на 10 документах и 40 test-вопросов на других 13. Разметка составлена агентом по источникам, без независимой проверки человеком. Проверен один положительный документ на вопрос; остальные документы не размечены исчерпывающе. Метрики оценивают нахождение опорной статьи, а не качество всех возможных ответов или полноту контекста.

Docker/Linux на Windows, Intel Core i5-1235U, 16 ГБ RAM, четыре потока PyTorch. Запросы выполнялись реальным API без второй копии ML-моделей. Обычный фон ноутбука и короткие unit-проверки могли влиять на задержку. Прогретые серверные таймеры включают Laya и reranker, исключают сеть HTTP и ожидание очереди. Загрузка моделей записана отдельно. Порог 0.8 фиксирован до запуска, по test не подбирался.

## Ограничения

Часть исходных страниц давала таймауты/HTTP 403; ошибки сообщаются без обхода авторизации и CAPTCHA. После исправления адаптера все 15 текущих N+1 получены успешно. Викторина не входит в корпус. Снимок мал и не является независимым доказательством качества в продакшне.

Полные сторонние тексты и модели не включаются в Git. Точный повтор требует сохранённого тома; свежие URL могут дать другой текст. CLI отклоняет корпус с хешем, отличным от манифеста разметки. Отчёты CLI сохраняются в доступный для записи `DATA_DIR/reports`.
